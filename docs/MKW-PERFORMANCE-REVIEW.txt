Mario Kart World PS5 performance review — 2026-11-02

Scope
This draft preserves the accumulated investigation, including experimental
instrumentation, as requested. The core remains Zortos 3140648a668aaebf87bae2dea17512fdca125ba0.
Maintained patch 0004 is incremental over the existing three patches. The
review branch is based on main 3c32faa and preserves its extracted-content
and Pokopia fixes. No core fork switch or driver binary is included.

The accumulated changes cover task/mesh shader handling, GPU mapping and
readback tracking, bounded texture uploads and ASTC decoding, staging
reclamation, targeted command completion, guest-memory/fiber/JIT budgets,
per-frame ordered-read telemetry, and faster native directory enumeration.
The latter scans metadata to construct the virtual RomFS; game contents are
still read on demand. Known files need one stat; known directories need none.
NFS/NTFS entries use followed stat outside the listing callback because the
shared interface may report zero file sizes and hold its own mutex.

Measured loading results
One bounded console run per candidate, using identical profiling schedules:
                         loader(s)  guest startup(s) first-frame total(s)
42 baseline                44.794       72.804             117.598
43 range-local mapping     44.801       34.745              79.546
45 mapping + metadata      32.732       33.583              66.315
Times are monotonic EDEN_STAGE durations from session start. First frame is
not title-ready time. Different randomized attract scenes prevent a matched
gameplay FPS comparison. Profiling itself adds overhead. Viewed captures
showed rendered title terrain/kart/background; title performance remained
around 13 FPS. Neither sustained 40 FPS nor 60 FPS has been achieved.

Early loading profiles were dominated by stat/lstat. Later profiles showed
full GPU mapping-table rebuild/sort work; range-local updates reduced that
work. The first FPS collapse preceded severe heap pressure. Texture/render
allocations and temporary ASTC decode images add pressure later, but the
measurements do not establish memory exhaustion as the sole loading cause.
The diagnostic driver's roughly 6 GiB sparse reservation aliases a single
2 MiB zero block; that reservation is not 6 GiB of eager physical allocation.

Direct mapped readback experiment (candidate 41)
Non-sparse allocations <=512 KiB, bounded 16 MiB live pool, persistent host
mapping and producer-range certificates. Only already-completed producers
qualify. GPU submission includes a HOST_READ visibility barrier; unfinished
or unknown writers fall back. Guest RAM is not imported. Asynchronous
snapshots retain staging. Mapping removes copies, not ordering requirements.

Console validation compared 21,242,192 bytes against staging with zero
mismatches. Five stationary Free Roam phases at Whistlestop Summit included
validation, baseline, direct, baseline, direct; 15 frames per phase. NPC
motion remained variable. Pooled baseline/direct windows, 30 frames each:
  FPS:                         13.1602 / 13.2011
  Ordered reads/frame:        230.633 / 231.8
  Completion CPU ms/frame:    43.8233 / 42.8957
  Queue delay ms/frame:       41.6296 / 40.6801
  Service ms/frame:            1.16084 / 1.16741
  GPU wait API ms/frame:       0.31765 / 0.32171
Direct mode removed exactly 20,224 GPU staging bytes/frame in both windows.
Buffer copies within ordered CPU-read callbacks were zero in both modes;
these downloads occur elsewhere. Ordered-read counts did not decrease and
no meaningful FPS gain was established. Overlapping CPU totals must not be
interpreted as a wall-clock frame breakdown. Cache visibility is validated
only for these tested ranges and driver, not every mapping or workload.

Review controls
EDEN_MKW_DIAGNOSTICS defaults OFF. Enable it explicitly at build time for
one-shot Mario Kart launch controls and intrusive snapshots/environment
probes. Some bounded core and CPU instrumentation remains compiled/enabled;
this is a broad research draft, not a claim of zero production overhead.
Published-semaphore and partial-readback experiments need further review.
The final merge onto current main and diagnostic gating have not been
console-tested; earlier experiment binaries are the runtime evidence.

Host validation
Patch reproduction: four patches, 127 touched files, matching the working
core. ASan/UBSan checks passed for mapped allocation policy, range tracker
(240,000 oracle queries), writer tracker (10,000 allocation lifetimes), and
native directory metadata including symlinks, malformed records and NFS.
Heap stress (including ThreadSanitizer), targeted GPU completion and staging
reclamation checks passed. The release hot-path check intentionally remains
failing because the accumulated draft retains experimental timers. The host
startup fixture now expects six progress slots and excludes the PS5 sampler
on non-PS5 hosts. Related CPU/JIT sampling arrays were also expanded to six
slots to fix an out-of-bounds read exposed by this fixture. See the PR description for the native build/check result.

Follow-up: separate frontend and backend queue delay
Reanalyzed all five complete candidate-41 captures (75 frames, 17,238 reads)
without modifying the original evidence. Total queue delay partitions into
3,064.440 ms before frontend pop and 30.657 ms between pop and backend start.
Total read-call time across threads was 3,396.993 ms. The analyzer now exports
both partitions per read, per frame and per read type, and checks their sum
against the existing queue duration whenever all timestamps are present.
These are overlapping thread durations, not a frame-wall-time decomposition.

The main semaphore site (guest PC 0x856894d0 at observational guest address
0x2106235000) accounts for 74–85% of each window's call time; another PC at
the same address adds time in two windows. Most observations changed value.
The longest read took 40.186 ms, including 40.160 ms before pop, about 1.8 us
between pop and service, and 8.9 us in service. A clean cache at service does
not prove that these reads could safely bypass earlier commands.

An older candidate-38 Free Roam profile contains Vulkan command handoff,
macro processing and fence-drain waits ahead of reads. It is not synchronous
with candidate-41 events, so it does not attribute each long read to a specific
command. Next runtime evidence should correlate preceding-command execution
with each long read, including forced fence drains and command handoffs.
No frame-rate gain is claimed from this analyzer change. Read-only console
status was idle during this follow-up; no deployment or restart was performed.
